## 2. REST API

요청자는 `X-User-Id` 헤더로 보냅니다. 사용자 등록·조회에는 이 헤더가 없습니다.
오류는 상태 코드와 상관없이 형식이 하나입니다.

```json
{ "code": "NOT_PROJECT_MEMBER", "message": "프로젝트 멤버가 아닙니다." }
```

`message`는 사람이 읽는 문장이고, `code`는 클라이언트가 분기에 쓰는 값입니다.

| code | 상태 | 언제 |
| :-- | :-- | :-- |
| `INVALID_REQUEST` | 400 | 입력값 검증에 걸렸습니다. 걸린 필드가 `message`에 붙습니다 |
| `ASSIGNEE_NOT_MEMBER` | 400 | 담당자로 지목한 사람이 그 프로젝트 멤버가 아닙니다 |
| `NOT_PROJECT_MEMBER` | 403 | 요청자가 그 프로젝트 멤버가 아니거나 없는 프로젝트 입니다 |
| `NO_PERMISSION` | 403 | 멤버지만 역할이 모자랍니다 |
| `USER_NOT_FOUND` · `TASK_NOT_FOUND` | 404 | 대상이 없습니다 |
| `DUPLICATE_EMAIL` · `ALREADY_MEMBER` | 409 | 이미 쓰는 이메일 · 이미 멤버입니다 |
| `LAST_OWNER` | 409 | 마지막 OWNER를 내리거나 빼려 했습니다 |
| `TASK_VERSION_CONFLICT` | 409 | 그 사이 다른 사람이 먼저 수정했습니다 |

### 엔드포인트 17개

| 메서드 | 경로 | 할 수 있는 사람 |
| :-- | :-- | :-- |
| POST · GET · GET | `/api/users`, `/api/users`, `/api/users/{userId}` | 누구나 (등록 · 목록 · 단건) |
| POST | `/api/projects` | 누구나. 만든 사람이 OWNER가 됩니다 |
| GET | `/api/projects` | 요청자가 속한 것만 나옵니다 |
| GET | `/api/projects/{projectId}` | 멤버 전원 |
| PATCH | `/api/projects/{projectId}` | OWNER · ADMIN |
| DELETE | `/api/projects/{projectId}` | OWNER |
| GET | `/api/projects/{projectId}/members` | 멤버 전원 |
| POST | `/api/projects/{projectId}/members` | OWNER · ADMIN (OWNER로 추가는 OWNER만) |
| PATCH | `/api/projects/{projectId}/members/{userId}` | OWNER · ADMIN (OWNER 임명·해임은 OWNER만) |
| DELETE | `/api/projects/{projectId}/members/{userId}` | OWNER · ADMIN (OWNER 제거는 OWNER만) |
| POST · GET · GET | `/api/projects/{projectId}/tasks` (+ `/{taskId}`) | 멤버 전원 (생성 · 목록 · 단건) |
| PATCH · DELETE | `/api/projects/{projectId}/tasks/{taskId}` | 담당자 본인 또는 OWNER · ADMIN |

작업 목록 파라미터: `keyword`(제목 검색) · `status` · `assigneeId` ·
`unassignedOnly`(담당자 없는 것만) · `page`/`size`(0부터, 기본 20) · `sort`(기본 생성 시각 역순)

요청 본문

| 요청 | 본문 |
| :-- | :-- |
| 사용자 등록 | `name`, `email` |
| 프로젝트 생성 · 수정 | `name`, `description`(선택) |
| 멤버 추가 · 역할 변경 | `userId`+`role` · `role` |
| 작업 생성 | `title`, `description`(선택), `assigneeId`(선택). 상태는 항상 `TODO`로 시작합니다 |
| 작업 수정 | `title`, `description`, `status`, `assigneeId`, **`version`(필수)** |

### 응답 예시

```json
{
  "id": 1, "projectId": 1,
  "title": "로그인 화면 퍼블리싱",
  "status": "IN_PROGRESS",
  "assignee": { "id": 3, "name": "박멤버" },
  "version": 2,
  "createdAt": "2026-08-26T10:12:33.482",
  "updatedAt": "2026-08-26T11:05:02.117"
}
```

`version`은 수정 요청에 그대로 실어 보내야 합니다. 동시수정 요청 문제를 해결하기 위한 필드로 수정할 작업 조회시점에 같이 조회되어 주어집니다.

프로젝트 응답에는 `myRole`(요청자 역할)이 함께 나갑니다. `myRole` 을 기준으로 요청자 권한에 맞는 기능의 버튼만 노출되도록 설계했고, 조회 시점에 역할을 검사하기에 클라이언트가 역할에 따른 버튼 노출을 서버에 다시 묻지 않아도 됩니다.

## 3. 주요 설계 결정

### 테이블과 계층

엔티티는 넷입니다.

| 테이블 | 담는 것 |
| :-- | :-- |
| `users` | 사용자. 인증이 없어 비밀번호 같은 필드는 두지 않았습니다 |
| `project` | 프로젝트 |
| `project_member` | **누가 어느 프로젝트에서 무슨 역할인가.** 역할이 여기 붙습니다 |
| `task` | 작업. 프로젝트에 속하고 담당자를 가집니다 |

역할을 `users`가 아니라 `project_member`에 둔 것이 이 설계의 중심입니다.
과제가 "같은 사용자라도 프로젝트가 다르면 역할이 다를 수 있다"고 했으니,
**역할은 사람의 속성이 아니라 사람과 프로젝트가 만나는 자리의 속성**입니다.
권한 판정도 전부 이 행을 찾는 일로 끝납니다. 없으면 비멤버이고, 있으면 그 역할로 판단합니다.

패키지는 `controller` · `service` · `repository` · `domain` · `dto` · `exception`으로
나눴습니다. 컨트롤러는 요청을 받아 넘기기만 하고, 권한 판정과 규칙은 전부 서비스에 둡니다.

### 명세에 없어 직접 정한 것

### 1. 동시 수정 — 낙관적 락 두 겹

읽는 순간 행을 잠가 다른 사람이 손대지 못하게 하는 **비관적 락**과, 잠그지 않고 저장 시점에
그 사이 바뀌었는지 확인해 거절하는 **낙관적 락** 중 어느 것을 쓸지 고민했습니다.
웹에서는 조회와 저장이 별개 요청이라, 비관적 락을 쓰려면 사용자가 화면을 보는 내내 잠금을
붙들고 있어야 합니다. 그러면 창을 열어 둔 채 자리를 비운 사람이 남의 수정을 막습니다.
같은 작업을 동시에 고치는 일이 드문 협업 도구에서는
**미리 막는 비용이 충돌을 나중에 알리는 비용보다 커서, 낙관적 락**을 쓰기로 했습니다.

구현은 두 겹입니다.

**겹 1.** 수정 요청에 `version`을 필수로 받아 서버가 DB 값과 직접 비교합니다.
A와 B가 같은 작업을 수정하고있단 가정에 A 와 B 모두 작업 조회시 같은 version 을 받습니다.
A가 화면을 보고 있는 사이 B가 저장을 끝내면, B의 수정으로 version 이 1 올라가고 A와의 version 이 차이가 생기게 됩니다.
이후 A가 저장을 시도하면 version 의 차이를 감지해 예외를 떨어뜨려 동시수정을 막습니다.
사람이 화면을 보는 시간이 길어 실제 충돌은 대부분 여기서 납니다.

**겹 2.** 엔티티의 `@Version`이 커밋 시점을 잡습니다. 수 ms 차이로 거의 동시에 같은 version을 든 두 요청이
겹 1을 모두 통과해 커밋할 때를 막습니다.


### 2. 그 밖의 결정

| 결정 | 이유 |
| :-- | :-- |
| **OWNER 임명·해임은 OWNER만 합니다** | 명세에는 부여 가능한 역할에 제한이 없습니다. 그대로 두면 ADMIN이 자신을 OWNER로 바꿔 **두 역할을 나눈 의미가 사라집니다.** 제거까지 묶은 것은 역할 변경만 막으면 우회로가 남기 때문입니다 |
| 작업 목록 필터를 제목 검색 · 상태 · 담당자로 정했습니다 | 협업에서 어떤 작업을 모아 살펴볼까 생각해보니 "내가 혹은 누군가가 맡은 일 보기" 와 "아직 아무도 안 맡은 일 찾기" 가 생각나 담당자 조건을 더했습니다. 그리고 작업 상태별로 진척도를 파악할 수 있도록 상태 조건을 더했습니다. |
| 멤버를 빼면 작업은 남기고 담당자만 비웁니다 | 함께 지우면 팀이 쌓은 내용까지 사라지고, 제거를 막으면 퇴사·이동을 처리할 수 없습니다 |
| `task`(작업) 의 담당자 외래키가 `users`(사용자)를 가리킵니다 | `project_member`(프로젝트별 멤버·역할)를 가리키면 프로젝트에서 멤버를 뺄 때 그 사람 작업이 함께 무너집니다. 이렇게 프로젝트에서 빠지기 전 수행한 작업 기록은 남기도록 했고, 대신 "지목한 사람이 이 프로젝트 멤버인가"는 서비스가 검사합니다 |
| 작업 상태는 `TODO`·`IN_PROGRESS`·`DONE` 세 가지입니다 | "안 함 / 하는 중 / 끝남"으로 상태가 명확하게 갈리게 구분 했습니다 |
| 작업 목록 시간순 정렬의 2차 기준으로 작업id를 사용했습니다 | 생성 시각은 값이 같을 수 있고, 그 경우 매번 순서가 흔들리는데, 페이지 사이에서 작업이 중복되거나 누락됩니다 |

## 4. 사용한 기술과 선택 이유

Java 17 · Spring Boot 3.3.13 · JPA · H2 · Gradle 8.14와 React는 과제 필수 스택이어서 사용했습니다.
여기에 더한 것은 셋입니다.

| 기술 | 왜 필요했나 |
| :-- | :-- |
| springdoc-openapi 2.6.0 | 과제가 요구한 Swagger UI 노출을 컨트롤러에서 자동으로 만들어 줍니다. 문서를 따로 쓰면 코드와 어긋납니다. 2.6.0이 Spring Boot 3.3에 맞는 버전입니다 |
| Lombok | 엔티티마다 생성자·게터가 반복됩니다. 가독성과 편의성을 위해 사용했습니다. |
| Vite | React 개발 서버가 필요한데, 백엔드를 건드리지 않고 `/api` 요청을 8080으로 넘기는 프록시를 설정 몇 줄로 얻습니다 |

동적 조건이 필요한 곳이 작업 목록 조회 한 군데뿐이라 QueryDSL은 넣지 않고
`(:param is null or ...)`로 처리했습니다.

### 테스트를 둔 곳

눈으로 놓치기 쉬운 곳에 두었습니다. 25건입니다.

- **동시 수정** 3건 — 손으로 재현하려면 타이밍을 맞춰야 하지만, 영속성 컨텍스트를 둘로 나누면 정확히 재현됩니다.
- **권한 규칙** 21건 — 역할 3종 × 기능 8종의 분기가 촘촘합니다. 비멤버 차단과 프로젝트 간 격리는 빠뜨려도 정상 흐름에서 드러나지 않습니다.
- **컨텍스트 기동** 1건 — 엔티티와 스키마가 어긋나면 여기서 걸립니다.

단순 CRUD와 DTO 변환은 테스트하지 않았습니다.

## 5. 회사별 데이터 분리(멀티테넌시)

멀티테넌시를 실제로 구축해 본 적은 없어, 흔히 쓰이는 세 가지 방식을 찾아보고
이 서비스의 규모를 가정해 골랐습니다.

**가정** — 회사 수는 수십에서 수백, 회사당 사용자는 수십 명, 법으로 물리적 분리를
요구받는 업종은 아니라고 봤습니다. 운영 인력도 많지 않다고 가정했습니다.

| 방식 | 나누는 위치 | 이 가정에서 |
| :-- | :-- | :-- |
| 공유 스키마 + `company_id` | 같은 테이블에 두고 컬럼으로 구분 | **채택.** 스키마가 하나라 운영 부담이 가장 적습니다 |
| 회사별 스키마 분리 | 스키마를 회사마다 따로 | 격리는 DB가 보장하지만, 회사가 늘 때마다 스키마를 만들고 마이그레이션을 모든 스키마에 돌려야 합니다 |
| 회사별 DB·서버 분리 | 물리적으로 분리 | 규제로 요구받을 때 씁니다. 운영 비용이 회사 수에 비례합니다 |

 공유 스키마는 격리를 **코드가 지킨다**는 것이 약점입니다. 조회 한 곳에서 조건을
 빠뜨리면 다른 회사 데이터가 나갑니다. 그래서 아래 2번을 함께 둡니다.

### 바꿀 곳

지금 격리 단위는 프로젝트이고, 그 위에 회사가 한 겹 생기는 구조입니다.

1. **테이블** — `company`(회사)를 만들고 `users`(사용자)·`project`(프로젝트)에
   `company_id`를 추가합니다.
2. **모든 조회에 회사 조건을 강제합니다.** 손으로 붙이면 한 곳만 빠뜨려도 격리가
   깨지므로, Hibernate `@Filter`처럼 자동으로 붙는 장치를 두는 편이 안전해 보입니다.
   다만 이건 문서로만 확인했고 직접 써 보지는 않았습니다.
3. **프로젝트에 멤버 추가 시 같은 회사인지 확인하고 사용자 정보에 회사명을 추가합니다.** 지금은 사용자 존재 여부만 봅니다.

지금은 조회 범위를 요청자 id와 프로젝트 id로 좁히는데, 같은 자리에 회사 id를
얹는 방식입니다.

## 6. 구현하지 못한 부분

명세에 있는 기능은 전부 구현했습니다. 시간이 더 있었다면 우선순위 순으로 아래를 했을 것입니다.

1. **작업 변경 이력.** 지금은 마지막 상태만 남아 누가 언제 무엇을 바꿨는지
   알 수 없습니다. 수정 시점마다 바뀐 필드와 이전 값을 남기면, 상태 흐름만 뽑아
   `TODO`에서 `DONE`까지 각 단계에 얼마나 머물렀는지 보는 것도 가능해
   작업현황 추적이 더 편할 것 같습니다.

2. **알림.** 담당자로 지정돼도 본인이 알 방법이 목록을 직접 여는 것뿐입니다.
   배정·상태변경·멤버제거처럼 남의 행동이 내 일에 영향을 주는 시점에는
   알려 주는 것이 좋을 것 같습니다.

3. **일정 관리.** 작업에 마감일이 없어 언제까지 해야 하는 일인지 알 수 없습니다.
   마감일을 더하고 목록에서 기한 임박·초과를 모아볼 수 있게 하면 좋을 것 같습니다.
